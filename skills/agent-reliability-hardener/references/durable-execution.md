# Durable Execution, Chaos Engineering, and CI Fault Injection

**Load this when:** you verify crash recovery and replay safety (Step 6), plan chaos drills and CI fault injection (Step 9), or capacity-plan the deployment.

## 1. What a Checkpoint Actually Gives You

Durable execution means the run's progress is persisted after every step, so a crash never loses completed work and an interrupted run resumes instead of restarting. The checkpointer writes atomically at every superstep boundary, and a checkpoint contains: the full graph state, the position in the graph (pending supersteps), and metadata (thread_id, checkpoint_id, timestamps, parent checkpoint ID forming the history chain).

Capabilities this unlocks:

- **Crash recovery:** the process dies mid-run, you resume with the same thread_id, and the graph continues from the last checkpoint.
- **Time travel:** read any historical checkpoint via `graph.get_state_history`, diff states, fork a new thread from an old checkpoint.
- **Background runs and double-texting:** a user sends a new message while the old run executes — reject it, enqueue it, or interrupt-and-resume; all three depend on the checkpointer.

## 2. At-Least-Once Semantics (the Part Everyone Gets Wrong)

LangGraph guarantees at-least-once execution of any node that started but did not checkpoint:

| Scenario | On resume |
|---|---|
| Node executed and checkpointed | Does NOT re-run |
| Node executed but crashed before checkpointing | Re-runs |

So in-flight tool calls whose result was never written are re-executed. Side effects inside nodes therefore need idempotency keys — exactly the same discipline as every other at-least-once system (Kafka consumers, SQS, Stripe webhooks). Anyone promising exactly-once end-to-end is selling you a lie your payment provider will happily disprove. Resume replay is `graph.invoke(None, {"configurable": {"thread_id": t}})` after fixing whatever was broken — no state reconstruction needed; this integration between your queue and checkpoint resume is the whole game.

Replay-safe tool rules:

- Every tool that mutates the outside world takes an `idempotency_key` parameter, passed by the graph, never generated by the model.
- Design idempotent entry nodes too — users see a half-finished reply and hit send again, so double-resume must not double-charge.
- Pin running threads to the graph version they started on: checkpoints are not portable across versions, and a deploy can strand in-flight runs with a checkpoint-schema mismatch at resume time.

## 3. Production Checkpointer Facts

| Checkpointer | Verdict |
|---|---|
| MemorySaver / InMemorySaver | RAM-only, loses everything on restart — fine for dev, poison for prod |
| PostgresSaver | Production default; async-capable; create tables via `.setup()` |
| SqliteSaver | Single-node deployments only |

Sharp edges:

- PostgresSaver caps the `thread_id` column at 255 chars — UUIDs are fine; long hashed compound IDs are not.
- Checkpoints accumulate forever: add a retention job deleting checkpoints older than N days, or the DB grows unbounded and every checkpoint write slows down.
- Checkpoint size is a latency tax on every superstep: a state channel accumulating unbounded history turns a 50ms write into 800ms, and you will blame the LLM for the slowdown. Trim, summarize, or move to the Store.
- Anything in state must be serializable by the checkpointer — `datetime`, `Decimal`, sets, and custom classes are the classic midnight crash ("works in dev" because in-memory checkpoints don't serialize). Enforce with a test that checkpoints and resumes every node.

## 4. Graceful Shutdown (Drain) and Double-Texting

LangGraph 1.2+ answers "my pod got a SIGTERM mid-run" with cooperative drain: `RunControl` + `request_drain()` stops a run between supersteps, saves a checkpoint, and raises `GraphDrained` with the reason; resume later with `invoke(None, config)`:

```python
control = RunControl()
signal.signal(signal.SIGTERM, lambda *_: control.request_drain("sigterm"))
try:
    result = graph.invoke(inputs, config, control=control)
except GraphDrained as e:
    log.info("drained: %s", e.reason)     # checkpoint saved; resume later
    # later, after redeploy:
    result = graph.invoke(None, config)   # resumes from checkpoint
```

Nodes can read `runtime.drain_requested` and `runtime.drain_reason` to skip expensive work when a drain is coming — the cooperative version of "wrap it up." Warning: drain does not cancel in-flight asyncio tasks or threads — a node stuck on a dead socket still blocks the process until its own timeout fires. Drain is a polite request, not a preemption mechanism; pair it with per-node timeouts and, for hard kills, process-level task cancellation.

Double-texting (new user message while the old run executes) needs one deliberately chosen strategy:

| Strategy | Behavior |
|---|---|
| Reject | Refuse the new input — the only strategy that never produces confusing interleaved outputs (underrated) |
| Enqueue | Run the new input after the current finishes |
| Interrupt | Kill the current run and start fresh — requires resumption from a stored checkpoint |

Pick one deliberately: interleaved state corruption is the failure mode of picking none.

## 5. Chaos Engineering for Agents

Fault injection in a controlled loop: hypothesize, inject, observe, fix. The drill catalog:

| Drill | Injection method | What it verifies |
|---|---|---|
| Kill a tool | Route tool calls to a stub that raises after N ms | Fallback path, error contract quality |
| Throttle the model | Proxy that delays/429s a percentage of calls | Backoff, breaker, user experience under latency |
| Corrupt state | Flip a field type in a checkpoint mid-run | Schema validation, crash recovery |
| Truncate tool output | Return first 10% of a large result | Does the agent notice missing data? |
| Kill process mid-run | SIGKILL the pod at random steps | Checkpoint resume correctness |
| Provider switch | Force fallback provider for an hour | Fallback prompt quality under real load |
| Poison one tool result | Inject a misleading result | Does the agent trust tool output blindly? |

The five-step drill loop: (1) state the hypothesis ("if search dies, runs degrade to cached answers under 500ms, no 5xx"); (2) inject the fault in staging against a canary of traffic; (3) observe what users saw and what the error rate and cost did; (4) fix the divergence from the hypothesis (usually the fallback path was never tested); (5) record the drill as a runbook entry plus an automated test.

Highest-value drills, in order:

1. **Mid-run SIGKILL** — teams are consistently surprised which side effects re-execute on resume. Discovering that "send welcome email" fires twice after a crash is exactly what the drill is for; the fix is always the idempotency discipline.
2. **Poisoned tool result** — reveals that most agents trust tool output completely.

## 6. Fault Injection in CI: The Four-Level Verification Ladder

A reliability mechanism that is not tested is a belief, not a mechanism. The ladder, cheapest first:

| Level | What | Cost | Catches |
|---|---|---|---|
| 1. Unit fault injection | Run the graph in CI with stubbed tools raising each catalog error (timeout, 429, 500, permanent) and assert the correct strategy fired: retry count, handler invocation, degrade path | Seconds, deterministic | Wrong retry predicates, missing handlers — ship in CI from week one |
| 2. Resume tests | Run the graph, kill it mid-run (or raise mid-node), resume from the checkpoint in a fresh process, assert the continuation matches the uninterrupted run modulo expected at-least-once re-execution | Cheap | Subtle checkpoint bugs nothing else catches: unserialized state fields, double-fired side effects |
| 3. Scheduled chaos drills | The Section 5 catalog, monthly, in staging; every drill's outcome becomes a runbook entry | Half-day cadence | Unknown unknowns before production finds them |
| 4. Shadow replay | Take real production thread IDs, replay in a sandbox with the mechanisms active, diff outcomes against recorded production outcomes | Expensive endgame | Regressions in the real distribution, not the synthetic one |

Teams that ship "we added retries" without level 1 discover in the first incident that the retry predicate never matched their actual exception class — the classic: the SDK wraps `TimeoutError` in `APIConnectionError`, and the retry policy watches for `TimeoutError` only. The exception you think your tool raises is not the exception it raises; the five-line test catches it every single time.

A resume test worth writing (interrupt every node in a test graph, kill the process, resume, and assert state identical to an uninterrupted run) — resume is the feature you are betting your reliability story on; test it like it owes you money.

## 7. Capacity Planning for Agents

- **Concurrency model:** a run holds one thread/connection per in-flight LLM call and tool call — 1,000 concurrent runs at 4 parallel calls each equals 4,000 concurrent outbound calls. Compute the binding constraint across provider RPM/TPM limits and tool-service limits (usually the LLM provider's tokens-per-minute on the mid-tier model, or one legacy tool).
- **Queue vs reject at capacity:** queue briefly (~30s, with visible progress) then reject with an apology; never unbounded queues. Queueing builds latency debt; rejecting is honest but user-visible.
- **Degraded-mode multiplier:** a provider outage that pushes all traffic to the fallback will 429 the fallback within minutes unless the fallback route also throttles and queues — capacity-plan the degraded mode, not just the happy mode.
- **Load testing with real mixes:** replay a corpus of ~1,000 recorded production runs at increasing concurrency, measure p95 latency and error rate at each step, find the knee. Synthetic uniform inputs will lie to you — the mix is the test.
- **First production week state:** every tool classified and every write tool keyed; retry + timeout policies on every external-facing node with predicates unit-tested against real exception types; the degradation ladder wired to a flag and reachable without redeploys; total-run deadline from the latency budget; PostgresSaver with retention, SIGTERM drain handler, and a once-tested resume-on-startup; the ten reliability-interview questions answered in writing; a scheduled first chaos drill two weeks out — before the first real incident, not after.

## 8. Operating Routines That Keep It Reliable

Reliability is maintained by routines, not heroics (~one day per month total):

| Cadence | Routine |
|---|---|
| Daily (5 min) | Dashboard glance: cost per run vs baseline, error rate by node, retry-rate trend (the earliest outage signal — rising retries mean something is degrading, usually days before it fails) |
| Weekly (30 min) | Failure review: top 10 failed/degraded runs read as traces; output becomes eval dataset rows and signature-library entries — the single habit that compounds most |
| Monthly (half day) | One chaos drill from the catalog, hypothesis-first, documented into runbooks; SLO review: budget burned, why, and whether the freeze applies |
| Quarterly (a day) | Reliability audit: re-ask the ten interview questions (the answers change as tools and traffic change), re-drill the degradation ladder end-to-end, check checkpoint retention and DLQ health, renegotiate SLO targets |
